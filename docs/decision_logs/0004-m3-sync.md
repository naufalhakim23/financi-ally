# 0004 — M3 sync, budgets, and the text-id migration

**Date:** 2026-07-27 · **Status:** shipped. Backend verified (tests + curl);
mobile compiles (`tsc` clean), on-device run pending a dev-client build.

## What landed
- **`internal/sync`** — WatermelonDB pull/push. `Pull` filters by server
  `updated_at > lastPulledAt`, splits created/updated, enumerates soft-deleted
  ids. `Push` reuses `ledger.Post` (balance invariant + ownership) and
  `budget.Set` so pushed records can't bypass the REST validation; invalid
  records are reported per client id, never silently dropped.
- **`internal/budget`** — monthly category targets + live spent rollup (Σ debit
  lines on the account in-month). Budgets soft-delete (`005`) so sync can
  communicate deletions. Endpoints: set/list/update/delete.
- **Migration `004_text_ids`** — accounts/entries/journal_lines/budgets PK +
  cross-FKs `uuid → text`, `DEFAULT gen_random_uuid()` dropped. `users.id`
  stays uuid (server-authoritative at register, not synced).
- **Mobile** — WatermelonDB schema/models/db/sync, authed fetcher
  (`reqAuthed`, 401-refresh-once via an auth bridge singleton), four screens
  (dashboard, pockets, budgets, add-entry) in an authed `(app)` tab group.
  `experimentalDecorators` enabled for WMB's model DSL.

## The load-bearing decision: text IDs
WatermelonDB is built around **client-generated IDs that the server stores
verbatim** (confirmed vs WMB FAQ + issue #216). Native sync breaks if the
server reassigns ids. Our M2 schema used server UUID PKs — incompatible.

Boss chose **Full WMB**, so the price was migrating synced tables to text PKs
and accepting client ids. Cost: migration `004`, API id format `uuid→string`
on those tables, `Post()`/`EntryInput`/`LineInput` accept client ids (server
generates a uuid only when the REST path omits one). Go models already used
`string` ids, so the Go layer barely moved. `users` stays uuid.

Rejected: hybrid client→server id mapping (issue #216's pain path; fragile,
fights WMB); spike with a non-WMB queue (keeps uuids but isn't WMB).

## Key decisions
- **Single-currency entries, per-currency balance.** Cross-currency (FX) is M4;
  an explicit FX entry with stored rate. `Post` rejects mixed-currency legs in M3.
- **Push reuses the service layer, not bespoke SQL.** `pushEntry` assembles an
  entry's lines from the `journal_lines` delta and calls `ledger.Post`, so the
  invariant, ownership, and currency match apply identically to REST and sync.
- **journal_lines are immutable, no timestamps.** They're created with their
  entry and never update; pull filters them on the parent entry's `created_at`,
  and there is no "updated"/"deleted" delta for them.
- **LWW = server `updated_at` stamp, single-user.** Money amounts never merge
  (posted entries are write-once); only metadata mutables (account name, budget
  target) can conflict, settled last-write-wins. Vector clocks are the upgrade
  if true concurrent multi-device metadata edits ever matter (they don't here).

## Verification
Backend: `go test -p 1 ./internal/...` (auth, ledger, money, sync; `-p 1`
because integration tests share one DB and each truncates). Sync tests:
push→pull round-trip, unbalanced push reported per-id. Curl e2e: sync push
(account + balanced entry) → pull returns them; budget `spent_minor` reflects
the sync-pushed entry (sync→ledger→budget chain).
